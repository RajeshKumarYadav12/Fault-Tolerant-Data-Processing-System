└──────────────────────────────────────────────────────────────────────────────┘

"How do you prevent double-counting?"
└─ Content-based fingerprinting. Same event always produces same SHA256 hash.
   Database rejects duplicates by fingerprint. Prevents double-count on retry.

"What if the database fails mid-request?"
└─ Atomic check-and-set ensures no partial writes. Either event is fully
   persisted or fully rejected. Client can safely retry. Idempotency via
   fingerprint prevents duplicate insertion.

"How do you handle unreliable timestamps?"
└─ Normalize malformed timestamps to current time. Include timestamp in
   fingerprint for idempotency. System remains consistent even with bad data.

"How does it scale?"
└─ This demo is single-instance for clarity. Production path:
   - PostgreSQL with UNIQUE constraint on fingerprint
   - Kafka for ingestion buffering & parallelism
   - Sharding by client_id for horizontal scale
   - Materialized views for aggregation
   - Redis caching for hot queries

"What would you improve?"
└─ 1. Persistence (PostgreSQL)
   2. Message queuing (Kafka)
   3. Distributed processing (Worker pools)
   4. Monitoring (Prometheus/Grafana)
   5. Analytics DB (ClickHouse)
   6. Multi-region replication
   7. Distributed consensus (Cassandra)

 consistency under unreliable client behavior and database failures."

Test First: Failure simulation (verify resilience) vs. assume (pray)
